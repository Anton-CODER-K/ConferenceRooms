   ConferenceRoomsDB

   Database/init.sql

   "ConnectionStrings": {
       "DefaultConnection":
           "Host=localhost;Port=5432;Database=ConferenceRoomsDB;Username=postgres;Password=..."
   }

4. Запустіть API.

# Conference Rooms API
Опис проєкту
Розроблено REST API для керування конференц-залами, їх бронюванням, додатковими послугами та розрахунком вартості оренди.
Основна задача системи дозволити користувачам знаходити доступні конференц-зали, створювати бронювання та автоматично розраховувати вартість з урахуванням часових тарифів і додаткових послуг.
Окрім основного функціоналу, було реалізовано авторизацію, оновлення токенів, звітність та розділення відповідальності між шарами застосунку.
Архітектура
Для проєкту використано багатошарову архітектуру:
 - Controller 
 - Service
 - Repository
 - PostgreSQL

Controller
Controller відповідає тільки за роботу з HTTP:
- отримання параметрів запиту;
- авторизацію користувача;
- виклик відповідного Service;
- повернення HTTP-відповіді.
Бізнес-логіка в Controller не розміщується, щоб він залишався простим і зрозумілим.
Service
Service містить основну бізнес логіку.
Наприклад, під час створення бронювання він:
1. перевіряє вхідні дані;
2. перевіряє існування та доступність кімнати;
3. перевіряє конфлікти бронювання;
4. перевіряє доступність вибраних послуг;
5. розраховує вартість;
6. створює бронювання та пов'язані записи.
Таким чином бізнес-правила не залежать від HTTP або конкретного SQL.
Repository
Repository відповідає тільки за роботу з базою даних.
Для доступу до PostgreSQL використано ADO.NET/Npgsql, а не Entity Framework Core. Це дозволило мати прямий контроль над SQL-запитами та транзакціями.
DTO та Entity
DTO використовуються на межі API, а Entity — всередині застосунку.

Я використав такий підхід, щоб API-моделі не були напряму прив'язані до структури бази даних.
Це дозволяє змінювати внутрішню модель або структуру БД без необхідності змінювати API-контракти.
Авторизація
Для захисту API використано JWT Bearer Authentication.
Доступ розділений за ролями:
- звичайний користувач може створювати бронювання;
- адміністративні операції з кімнатами та послугами доступні адміністратору.
Також реалізовано Refresh Token.
Access Token має короткий термін життя, а Refresh Token використовується для отримання нового Access Token.
Refresh Token зберігається в базі у вигляді хешу. Це зроблено для того, щоб навіть при компрометації бази даних неможливо було безпосередньо використати збережений токен.
Транзакції
Транзакції використовуються там, де одна бізнес-операція змінює декілька таблиць.

Якщо друга операція завершиться помилкою, перша також буде відкотена.
Таким чином база не залишиться в частково зміненому стані.
Бронювання
Під час створення бронювання система перевіряє, чи немає іншого активного бронювання цього самого залу на заданий період.
Для перевірки використовується умова перетину інтервалів

Це дозволяє коректно визначити конфлікт між двома бронюваннями.
Також перевіряється, що вибрані користувачем послуги дійсно доступні для конкретної кімнати.
Розрахунок вартості
Логіку ціноутворення винесено в окремий PricingService.
Правила зберігаються в таблиці pricing_rules, а не прописані безпосередньо в коді.
Це було зроблено для того, щоб у майбутньому можна було змінювати тарифи без зміни програмного коду.
Наприклад:
06:00–09:00  → -10%
09:00–18:00  → стандартна ціна
12:00–14:00  → +15%
18:00–23:00  → -20%

Для ситуацій, коли декілька правил діють одночасно, використовується priority.
Наприклад, період 12:00–14:00 одночасно входить у стандартний період 09:00–18:00, але правило Peak має більший priority, тому використовується саме воно.
Збереження ціни послуг
При створенні бронювання ціна кожної вибраної послуги зберігається в booking_services.
Це потрібно для збереження історичної вартості.
Наприклад, якщо сьогодні проектор коштує:
500 грн

і клієнт створив бронювання, а завтра ціна змінилася на:
700 грн

старе бронювання все одно повинно залишитися з ціною 500 грн.

Soft Delete
Для кімнат і послуг використовується soft delete через поле:
is_active

Замість фізичного видалення запису:
DELETE FROM rooms

виконується:
UPDATE rooms
SET is_active = false

Я використав такий підхід, оскільки кімнати та послуги можуть бути пов'язані з історичними бронюваннями.
Фізичне видалення могло б призвести до втрати історичних даних або проблем із зовнішніми ключами.
Звіти
Було додано endpoint:
`GET /api/reports/rooms?from=2026-10-01&to=2026-10-31`

Він показує статистику по кожній кімнаті:
- кількість бронювань;
- кількість заброньованих годин;
- отриманий дохід.
Також розраховується загальна кількість бронювань та загальний дохід за період.
Звіт винесений в окремі ReportService та ReportRepository, щоб аналітичні SQL-запити не змішувалися з основною логікою бронювання.
Обробка помилок
Для централізованої обробки помилок використано ExceptionMiddleware.
Service може кинути, наприклад:
`throw new BusinessException("Room not found.");`

Middleware перетворює виняток у відповідну HTTP-відповідь.
Це дозволяє не дублювати try/catch у кожному Controller.
Чому використані інтерфейси
Інтерфейси використані там, де вони дають практичну користь, наприклад для Repository

Це дозволяє:
- замінити реалізацію;
- використовувати mock у unit-тестах;
- зменшити зв'язаність компонентів.
При цьому я не створював інтерфейс для кожного класу, оскільки це додавало б зайву абстракцію без практичної користі.
